# อัปโหลด ESP32 รุ่น 1.3.0

## รุ่นที่เตรียมไว้ตอนนี้

สำหรับ ESP32 Dev Module / ESP32-WROOM-32 แบบเดิม (ไม่ใช่ C3/S3)
ค่าเริ่มต้นเป็น **SIMULATION**: อัปโหลดและเชื่อมเว็บไซต์ได้โดยไม่ต้องต่อ LCD, RTC,
เซอร์โว หรือเซ็นเซอร์ และไม่ขยับมอเตอร์ ผลทดสอบมีหมายเหตุ `dry run`
ต้อง deploy backend และ frontend ชุดที่รองรับการแยกผลทดสอบด้วย

การ build ผ่านไม่ใช่ผลทดสอบกลไกจริง ยังไม่ได้ยืนยันจำนวนเม็ดหรือสอบเทียบฮาร์ดแวร์

## อัปโหลดจากคอมพิวเตอร์นี้

เปิด Terminal ในโฟลเดอร์ `smart-pill-dispenser`:

```sh
python3 tools/firmware.py ports
python3 tools/firmware.py upload --port /dev/cu.usbserial-0001
python3 tools/firmware.py monitor --port /dev/cu.usbserial-0001
```

เปลี่ยนชื่อพอร์ตตามผล `ports` และปิด Serial Monitor เดิมก่อน upload
`upload` จะ compile ซอร์สปัจจุบันใหม่ก่อนทุกครั้ง ถ้า compile ไม่ผ่านจะไม่ flash
ไม่ได้สั่ง erase flash จึงรักษาข้อมูล Wi-Fi คิวผล และประวัติป้องกันคำสั่งซ้ำใน NVS
ออกจาก monitor ด้วย Ctrl+C

หากต้องการเตรียมไฟล์อย่างเดียว:

```sh
python3 tools/firmware.py build
```

ได้ไฟล์ใน `build/esp32` พร้อม `upload-manifest.json` และ SHA256 ของ binary
ไฟล์ binary มีข้อมูลประจำเครื่องจาก `secrets.h` ห้ามนำขึ้น Git หรือแชร์สาธารณะ
ไม่ควร flash `*.bin` ด้วย offset ที่เดาเอง ให้ใช้สคริปต์ upload หรือ Arduino IDE

สคริปต์ค้นหา Arduino CLI ใน PATH หรือจาก Arduino IDE 2 บน macOS
เลือก CLI/config เองได้ด้วย `--cli` และ `--config`
เครื่องนี้ทดสอบกับ esp32 core **3.3.12**, FQBN `esp32:esp32:esp32`
ไลบรารีที่ใช้: ArduinoJson, ESP32Servo, DS1307RTC, Time, LiquidCrystal_I2C

## ตรวจหลังอัปโหลด ขณะยังไม่มีฮาร์ดแวร์

1. Serial 115200 ต้องแสดง `firmware 1.3.0` และ `Mode: SIMULATION (no motion)`
2. หากไม่มี Wi-Fi ที่บันทึกไว้ จะเปิด Setup เอง; หากมีแล้ว ใช้ GPIO33 ค้าง 3 วินาทีขณะว่างเพื่อเปิด Setup
3. ตั้ง Wi-Fi และจับคู่จากเว็บไซต์ตามคู่มือ QR Wi-Fi เดิม
4. `/status` ของกล่องบน LAN ต้องมี `wifi_connected=true`, `sync_ok=true`,
   `clock_valid=true`, `clock_source=SERVER` (เมื่อไม่มี RTC), `dry_run=true`,
   `servo_movement_enabled=false`
5. ใส่ยาทดสอบลงช่องบนเว็บและกำหนดเวลาในอนาคต จำนวนที่รองรับคือเม็ดเต็ม 1–9 เม็ด
   เมื่อถึงเวลาจะเตือนรอผู้ใช้กดรับยา GPIO33 สั้นแล้วปล่อย ไม่ได้ปล่อยยาเองทันทีตามเวลา
   หรือใช้คำสั่งจ่ายทดสอบจากเว็บ
6. รอ sync และดูปฏิทิน: ต้องขึ้นผล “ทดสอบ” และไม่นับเป็นจ่ายจริง
   ปฏิทินอัปเดตทุก 15 วินาทีขณะเปิดดู; การรับคำสั่งอาจรอรอบ sync ประมาณ 60 วินาที
7. คิว `pending_events` ต้องกลับเป็น 0 หลัง server รับผล

หากไม่มี RTC หลังรีบูตต้องรอ sync เวลาใหม่; เวลาจาก RAM ไม่คงอยู่ขณะไฟดับ
สถานะ ONLINE หมายถึงติดต่อ server ได้ ไม่ได้ยืนยันการนับเม็ด

## เมื่อมีฮาร์ดแวร์แล้ว

ใช้ผังใน `docs/ESP32_WIRING.md` และตรวจรุ่น/แรงดันของโมดูลจริงก่อนต่อ
ค่า pin จาก config ปัจจุบัน:

| หน้าที่ | GPIO |
|---|---|
| ปุ่มรับยา / Setup, เลื่อน, ยกเลิก | 33, 32, 27 |
| Servo ช่อง 1–3 | 18, 19, 23 |
| IR ช่อง 1–3 | 34, 35, 36 |
| DRV8833 PWM ช่อง 1–3 | 13, 26, 4 |
| DRV8833 DIR ช่อง 1–3 | 16, 17, 14 |
| I2C SDA / SCL | 21 / 22 |
| Buzzer | 25 |

**ต้องสอบเทียบก่อนใส่ยา**: รุ่นเซอร์โว/ชนิดการหมุน, ตำแหน่งพักและจ่ายแต่ละช่อง,
เวลาเดินทาง, สัญญาณ IR เมื่อว่าง/ถูกบัง, หนึ่งเม็ดนับหนึ่งครั้ง, การหยุดและการกลับตำแหน่งพัก
ค่าตัวอย่าง 1500/1750 µs และ 700 ms ไม่ใช่ค่าที่รับรองกับกลไกของคุณ

คัดลอก `ESP32_Main/hardware.example.h` เป็น `ESP32_Main/hardware.local.h`
กรอกค่าที่วัดจริงใน `PILLBOX_REST_PULSES`, `PILLBOX_RELEASE_PULSES`, `PILLBOX_MOVE_TIME_MS`
หลังสอบเทียบครบแล้วจึงตั้ง `PILLBOX_CALIBRATED=true` และ `PILLBOX_REAL_HARDWARE=true`
ถ้าเปิดมอเตอร์โดยยังไม่ยืนยันการสอบเทียบ compile จะหยุด
โหมดจ่ายจริงจะปิด dry run อัตโนมัติ ไม่ต้องแก้สอง flag แยกกัน
จากนั้น build/upload ใหม่และตรวจ Serial ว่าเป็น `Mode: HARDWARE (motion enabled)`

ต้องทดสอบตั้งแต่เว็บ → บอร์ด → จำนวนเม็ดจริง → server → ปฏิทิน โดยใช้วัสดุทดสอบก่อนใช้งานจริง

## พฤติกรรมป้องกันที่เพิ่ม

- ระหว่างกลไกทำงาน งด HTTP, หน้าเว็บภายใน และการรีเฟรช LCD/RTC เพื่อให้วนอ่านปุ่มหยุดและ IR ได้ต่อเนื่อง
  หน้า `/status` และคำสั่งยกเลิกจากเว็บอาจรอจนกลไกหยุด; ปุ่มยกเลิกที่บอร์ดยังทำงาน
- ไม่ปัดจำนวน 0.5/1.5 เม็ดขึ้นเป็นจำนวนเต็ม แต่ปฏิเสธก่อนเริ่มกลไก
- IR ถูกบังก่อนเริ่มจะปฏิเสธ; เมื่อนับครบจะสั่งกลับตำแหน่งพักและเบรกการสั่นทันที
- จ่ายเกิน จ่ายไม่ครบ หรือยกเลิกระหว่างรอบ ส่ง `FAILED` พร้อมจำนวนที่ตรวจพบ/จำนวนที่สั่ง
  มื้อนั้นจะไม่กลับมาให้กดจ่ายเต็มจำนวนซ้ำอัตโนมัติ ต้องตรวจเม็ดที่ออกแล้วก่อนออกคำสั่งใหม่
- จอง ID คำสั่งจ่ายและมื้อยาจริงใน NVS ก่อนเริ่มกลไก ป้องกันการสั่งซ้ำเมื่อรับคำสั่งเดิมหรือรีบูต
  เก็บได้ 64 รายการและใช้ช่องเก่าซ้ำได้เมื่อพ้น 24 ชั่วโมง; ถ้าเต็ม/เขียนไม่ได้จะไม่เริ่มจ่าย
  คำสั่งบน server มีอายุ 15 นาที จึงสั้นกว่าช่วงเก็บประวัติ
- หากไฟดับหลังจองรอบแต่ก่อนส่งผล อาจไม่มีผลสุดท้ายบน server และคำสั่งอาจหมดอายุ
  จะไม่สั่งรอบเดิมใหม่เอง ต้องตรวจจำนวนยาและกลไกจริงก่อนออกคำสั่งใหม่
  NVS ไม่สามารถบอกได้ว่ายาตกจริงระหว่างไฟดับกี่เม็ด และการ erase flash จะลบตัวป้องกันนี้

## ผลตรวจด้วยซอฟต์แวร์

```sh
python3 -m unittest discover -s tests -p 'test_*.py' -v
python3 tools/firmware.py build
```

ชุดทดสอบจำลอง GPIO/เวลา/เครือข่าย/NVS เพื่อทดสอบตรรกะ ไม่ได้ใช้แทนการวัดสัญญาณหรือทดลองกลไกจริง

## รุ่น 1.3.0: รวมการจ่ายหลายช่องจาก GitHub

รวมฐาน `ed4b32f` กับนาฬิกาโดยไม่มี RTC, การแยกผล dry run และตัวป้องกันจ่ายซ้ำในเครื่อง

- กดเขียวสั้นหนึ่งครั้งรับมื้อที่กำลังเตือนหลายช่อง จ่ายพร้อมกันสูงสุด 2 ช่อง และคิวช่องที่เหลือจะเริ่มเมื่อมีที่ว่าง
- หน่วงคำสั่งเริ่มช่องถัดไป 250 ms ตามค่า `DISPENSE_STAGGER_MS`
- สถานะ `Queued` แยกมื้อที่ตอบรับแล้วออกจากมื้อที่กำลังเตือน ป้องกันการกดรับซ้ำขณะรอ
- จองรอบยาจริงทุกช่องลง NVS ก่อนเริ่มมอเตอร์ตัวแรก ไม่จองซ้ำเมื่อคิวได้ช่องว่าง
- ปุ่ม Cancel หยุดช่องที่ทำงานและยกเลิกช่องที่รอทันที แม้กดสั้น ไม่ปล่อยให้ช่องที่สามเริ่มตามหลัง
- ปุ่มเลื่อน/ข้ามก่อนรับยาใช้กับทั้งรอบ หากมีมื้อใดเลื่อนไม่ได้จะไม่เลื่อนบางส่วน
- ผลจากช่องที่เสร็จก่อนพักใน RAM จนทุกมอเตอร์หยุด จึงเขียน NVS และส่ง server
  หากไฟดับระหว่างนี้อาจเสียผลที่ยังอยู่ใน RAM; การจองรอบใน NVS ยังป้องกันการจ่ายรอบเดิมซ้ำ
- จำนวนเม็ดเกิน/ขาดและ IR ที่ถูกบังยังแสดงความล้มเหลว ไม่ถือว่าจ่ายสำเร็จ

ชุดทดสอบเพิ่มการเชื่อมปุ่ม ตารางยา ตัวควบคุมหลายช่อง และคิวผลเข้าด้วยกัน
ครอบคลุมโหมดจำลองและเส้นทางโหมดฮาร์ดแวร์ด้วย GPIO/servo จำลอง
ยังต้องวัดกระแสและทดสอบแหล่งจ่ายจริงก่อนเปิดมอเตอร์สองช่องพร้อมกัน ค่ากระแสใน config เป็นสมมติฐานของการออกแบบ
