ผู้ใช้เลือกอุปกรณ์ของบัญชี กำหนดยาประจำช่องและจำนวนต่อรอบ แล้วสร้างเวลาและวันที่ใช้งาน ก่อน
ตรวจสถานะเปิดใช้แต่ละช่อง ตารางและประวัติผูกกับข้อมูลของบัญชี ชื่อ IntakeLog ในฐานข้อมูลใช้เก็บ
ผลการทำงานตาม API จึงไม่ควรแปลความว่าบุคคลรับประทานยาแล้วโดยอัตโนมัติ [6]
ภาพที่ 3.8 ลำดับการรับข้อมูลและส่งเหตุการณ์ [5], [6]
ตามภาพที่ 3.8 ESP32 ส่ง GET /api/device/sync เพื่อรับเวลา ตารางและคำสั่ง แล้วตรวจและพัก
ข้อมูลก่อนนำมาใช้ การรอ GET /api/device/wait ใช้แจ้งว่าข้อมูลเปลี่ยน โดยกำหนดเวลารอสูงสุด 
15 วินาที และซิงก์เต็มอย่างช้าในรอบ 10 นาที หาก /wait ไม่รองรับจึงกลับไปสอบถามตามรอบพื้นฐาน 
5 วินาที เมื่อซิงก์ล้มเหลวกำหนดรอลองใหม่ 15 วินาที ส่วนคิวผลพยายามส่งทุก 10 วินาที ค่าทั้งหมด
อาจได้รับผลจากสถานะเครือข่ายและงานที่ค้าง ไม่ใช่การรับประกันเวลาตอบสนอง
ก่อนนำคำสั่ง DISPENSE ออกจากคิว เฟิร์มแวร์จอง Command ID ใน NVS หากจองไม่ได้จะไม่เริ่มคำ
สั่ง การจองไม่ใช่การตอบรับว่าจ่ายสำเร็จ เมื่อกลไกสิ้นสุดจึงสร้างผลจริงหรือผลตามโหมด พร้อม Event 
ID แล้วส่ง POST /api/device/events รายการที่เซิร์ฟเวอร์ตอบรับจึงถูกนำออกจากคิว ส่วน ACK 
ใช้กับคำสั่งที่ไม่ใช่การจ่ายบางชนิด
สำหรับรอบตามตาราง เมื่อเปิดกลไกจริง pill_app.cpp จองคีย์ dose ที่ประกอบด้วย schedule ID 
วัน และโหมดก่อนจัดคิว หากจองไม่ได้จะรายงาน FAILED พร้อมข้อความให้ตรวจยา ส่วน dry run ไม่
จองคีย์นี้ในเส้นทางดังกล่าว ทะเบียนรองรับ 64 รายการและเก็บตามช่วง 86,400 วินาทีโดยต้องมีเวลา
ที่ใช้ได้ จึงไม่ควรอ้างว่าป้องกันซ้ำได้ตลอดไปหรือยืนยันจำนวนที่ออกเมื่อไฟดับ
ทะเบียนคำสั่งลดการทำคำสั่งเดิมซ้ำ แต่ไม่ใช่การรับประกันจำนวนเม็ดยาแบบสมบูรณ์เมื่อไฟดับกลางรอบ 
การกู้สถานะต้องตรวจทั้งผลบนเซิร์ฟเวอร์และจำนวนยาที่ออกจริง
